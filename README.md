## Архітектура сутностей (Lab 02)

### `src/math/vector2.js`

Незмінний (immutable) 2D-вектор `Vector2`.

Усі методи (`add`, `sub`, `scale`, `normalize`, `distanceTo`, `clone`) не мутують ні `this`, ні переданий аргумент, а повертають новий екземпляр `Vector2`.

### `src/entities/entity.js`

Базовий клас `Entity` із приватним полем `#id` (генерується модульним лічильником `nextId`), публічним геттером `get id()`, векторами позиції `pos` та швидкості `vel`, радіусом `radius`, типом `kind`, прапорцем `dead` та методом `markDead()`.

### `src/entities/ship.js`

Клас `Ship extends Entity` (єдиний рівень наслідування).

Містить:

- приватні поля `#hp`, `#fireCd`, `#respawnTimer`;
- публічний геттер `get hp()`;
- метод `fire(world)` (спавн кулі з носа корабля з урахуванням власної швидкості);
- метод `takeDamage()`;
- автоматичний респаун у центрі арени через 2 секунди.

### Інші сутності

- `src/entities/bullet.js` — кулі мають час життя (TTL = 1.4 с).
- `src/entities/asteroid.js` — астероїди.
- `src/entities/particle.js` — частинки вибуху (`spawnExplosion`), які згасають із часом.
- `src/entities/pickup.js` — бонуси.

Усі сутності першого рівня наслідування походять від `Entity`.

### `src/world.js`

Сховище сутностей `World` поверх `Map<id, Entity>` із методами:

- `spawn()`;
- `despawn()`;
- ітератором `[Symbol.iterator]()`;
- генератором `*ofKind(kind)`.

Реалізовано патерн **mark-and-sweep**: під час кроку зіткнення лише позначають сутності (`markDead()`), а фізичне видалення з `Map` відбувається наприкінці `World.step()`.

### `src/systems/collision.js`

Окрема система перевірки зіткнень коло-коло `circleCircle(aPos, aR, bPos, bR)` без `Math.sqrt` (порівняння квадратів відстані та суми радіусів).

## Проблема втрати `this` у `ship.fire` та способи виправлення

У JavaScript значення `this` визначається не місцем оголошення методу, а способом його виклику.

Існують чотири правила прив’язки:

1. За замовчуванням.
2. Неявна прив’язка через об’єкт.
3. Явна прив’язка через `call`, `apply` або `bind`.
4. Прив’язка через `new`.

### У чому баг?

Якщо передати метод об’єкта напряму як колбек у слухач подій:

```javascript
// ПОМИЛКА: передаємо посилання на функцію без контексту об'єкта
window.addEventListener("keydown", player.fire);
```

Коли браузер викличе цей колбек при натисканні клавіші, метод буде викликано без об’єкта зліва від крапки (спрацює правило прив’язки за замовчуванням).

Оскільки ES-модулі та тіла класів завжди працюють у `strict mode`, `this` дорівнюватиме `undefined` (а аргументом замість `world` прийде об’єкт `KeyboardEvent`).

Спроба прочитати `this.isAlive` або `this.pos` призведе до помилки:

```text
TypeError: Cannot read properties of undefined
```

### Три способи виправлення

#### 1. Стрілкова функція-обгортка (використано в `src/main.js`)

```javascript
window.addEventListener("keydown", (e) => {
	if (e.code === "KeyE") player.fire(world);
});
```

Стрілкова функція не має власного `this`, а всередині її тіла `player.fire(world)` викликається як метод об’єкта `player` (неявна прив’язка: `this === player`).

#### 2. Явна прив’язка через `Function.prototype.bind`

```javascript
const fireBound = player.fire.bind(player, world);
```

`bind` створює нову функцію з назавжди зафіксованим `this = player` та частково застосованим аргументом `world`.

#### 3. Оголошення методу як поля класу зі стрілковою функцією

```javascript
fire = (world) => {
	// ...
};
```

Це прив’язує `this` до екземпляра під час створення в конструкторі, проте створює окрему копію функції на кожен екземпляр замість одного методу в `Ship.prototype`.

## Дизайн-запис: Композиція проти глибокого дерева наслідування

### Як виглядала б глибока ієрархія класів (проблема)

Якби ми будували архітектуру через класичне наслідування (`extends`), додавання двох нових фіч — самонаведення (`Homing`) та бонусів на карті (`Pickup`) — зламало б дерево класів:

```text
Entity
 ├── Ship
 ├── Projectile
 │    ├── Bullet
 │    └── HomingBullet        <-- дублювання логіки наведення
 ├── Obstacle
 │    ├── Asteroid
 │    └── HomingAsteroid      <-- вдруге пишемо ту саму математику повороту!
 └── Item
      └── Pickup              <-- не рухається, але наслідує vel та фізику руху
```

Таке дерево породжує дві класичні проблеми ООП:

#### Комбінаторний вибух підкласів

Якщо самонаведення потрібне і для ракети/кулі, і для магнітного астероїда, у моноієрархії без множинного наслідування доводиться або дублювати код у `HomingBullet` та `HomingAsteroid`, або піднімати `homing` у базовий `Entity`, засмічуючи ним звичайні частинки вибуху й бонуси.

#### Порушення принципу підстановки Лісков (LSP) для `Pickup`

Бонус `Pickup` стоїть на місці, має радіус колізії, підбирається кораблем, але не є ані кораблем, ані снарядом.

У жорсткій ієрархії йому довелося б успадковувати непотрібні поля руху чи зброї.

### Чому вибрано композицію (наше рішення)

Ми обмежили наслідування одним рівнем (`Entity` → конкретна сутність), а поведінки реалізували через композицію (**«has-a» замість «is-a»**).

#### `Homing` (`src/components/homing.js`)

Незалежний компонент із методом `apply(entity, world, dt)`.

Будь-яка сутність, що має `pos` і `vel` (куля або астероїд), може тримати посилання `this.homing = new Homing(...)` і делегувати йому коригування вектора швидкості.

Поведінку можна вмикати або вимикати динамічно під час гри.

#### `Pickup` (`src/entities/pickup.js`)

Легка сутність без зайвої ієрархії, яка зберігає лише тип ефекту (`score`, `heal`, `homing`), а взаємодія з кораблем обробляється в системі колізій `World`.

## Експеримент із ланцюжком прототипів у консолі

Перевірка побудови ланцюжка прототипів для екземпляра `player = new Ship(...)` у DevTools:

```javascript
Object.getPrototypeOf(player) === Ship.prototype;
// true

Object.getPrototypeOf(Ship.prototype) === Entity.prototype;
// true

Object.getPrototypeOf(Entity.prototype) === Object.prototype;
// true

Object.getPrototypeOf(Object.prototype);
// null
```

### Перевірка власних та успадкованих методів

```javascript
player.hasOwnProperty("pos");
// true (власне поле екземпляра)

player.hasOwnProperty("fire");
// false (метод лежить у Ship.prototype)

player.hasOwnProperty("markDead");
// false (метод лежить у Entity.prototype)
```

## Reflection (Питання до захисту)

### Чому `Map<id, Entity>`, а не масив `Entity[]`?

Пошук, отримання (`world.get(id)`) та видалення сутності за `id` у `Map` працюють за `O(1)`, тоді як у масиві потребують лінійного пошуку `O(n)` (`findIndex` / `splice`).

Крім того, `Map` гарантує унікальність ключів і зберігає порядок вставки під час ітерації.

### Навіщо патерн mark-and-sweep (позначка `dead` і видалення в кінці кроку)?

Якщо видаляти об’єкти з колекції прямо під час перевірки колізій у вкладених циклах, можна пропустити частину перевірок або порушити логіку, коли одна куля або астероїд бере участь у кількох подіях у межах одного тіку.

Позначка `markDead()` відкладає фактичне видалення до завершення всіх систем кроку.

### Як працюють приватні поля `#id` та `#hp` у JavaScript?

Синтаксис `#field` забезпечує жорстку інкапсуляцію на рівні рушія JS (а не лише домовленість як `_field`).

Звернутися до `ship.#hp` ззовні класу `Ship` синтаксично неможливо, а в підкласах `#id` з `Entity` також недоступне напряму — лише через публічний геттер `get id()`.

### Чому методи `Vector2` зроблені чистими (незмінними)?

Якби `vel.scale(dt)` мутував вектор на місці, виклик:

```javascript
this.pos = this.pos.add(this.vel.scale(dt));
```

зіпсував би швидкість `this.vel` корабля.

Незмінність усуває приховані побічні ефекти при передачі векторів між сутностями.
