Серверна частина мультиплеєрної гри на Node.js (`node:http`, `ws`, `node:events`, `node:stream`) у структурі **npm workspaces** (`client/` + `server/`).

Реалізовано:
- керування кімнатами через `EventEmitter`;
- WebSocket-протокол входу, виходу й живого чату з валідацією повідомлень;
- heartbeat-перевірки;
- контроль *backpressure*;
- потокове логування подій матчу у форматі NDJSON через `Transform` + `stream.pipeline`.

## Архітектура сервера та клієнтського сокета

### `server/src/index.js`

HTTP-сервер на `node:http`:

- відхиляє запити з `..` (path traversal → `400 Bad Request`);
- `GET /health` — повертає стан сервера, аптайм, кількість кімнат та споживання пам’яті `rss`;
- `GET /api/rooms` та `POST /api/rooms` — список і створення кімнат;
- `GET /api/replays/:id` — потокова віддача NDJSON-логу через `stream.pipeline`;
- роздає зібрану статику з `client/dist`;
- коректно завершує роботу за `SIGINT` / `SIGTERM`: закриває WebSocket-з’єднання (`1001`), дописує буфери логів на диск і виходить з кодом `0`.

### `server/src/room.js`

`class Room extends EventEmitter`:

- зберігає клієнтів кімнати;
- розсилає повідомлення чату й системні події;
- якщо `ws.bufferedAmount > 64 КБ`, повільному клієнту зайві пакети не шлються (backpressure);
- порожня користувацька кімната генерує подію `"empty"` і видаляється.

### `server/src/wsServer.js`

WebSocket-сервер (`ws`).

#### Валідація повідомлень

| Умова | Код закриття | Поведінка |
|---|---:|---|
| Бінарний формат | `1003` | Відхиляється |
| Перевищення розміру > 4 КБ | `1009` | Відхиляється |
| Перевищення ліміту > 20 повідомлень/с | `4008` | Відхиляється |
| Битий JSON або невалідна форма | `1007` | Відхиляється |
| Невідомий тип повідомлення | `4003` | Відхиляється |
| Очікування першого повідомлення `join` довше 5 секунд | `4001` | З’єднання закривається |

#### Heartbeat

- сервер надсилає `ping` раз на 15 секунд;
- при 2 пропущених `pong` розриває з’єднання через `ws.terminate()`.

### `server/src/logger.js`

`NdjsonStringifyTransform extends Transform` + `stream.pipeline` для запису логів матчу (`match-<roomId>.ndjson`).

Функція `streamReplayFile` забезпечує потокову віддачу реплеїв без читання файлу цілком у RAM.

### `client/src/net/socketClient.js`

Обгортка над браузерним `WebSocket` із:

- чергою повідомлень `send` (поки сокет у стані `CONNECTING`);
- автоматичним перепідключенням з експоненційною затримкою:

```text
500 мс * 2^attempt + jitter
```

## Графік пам’яті (rss) під час потокового завантаження логу (Backpressure)

Експеримент проведено скриптом `node scripts/bench-replay-rss.js`.

Згенеровано NDJSON-файл обсягом **36.6 МБ (250 000 подій)**, після чого повільний HTTP-клієнт завантажував його через `GET /replay` із затримкою 2 мс на кожен чанк.

Завдяки `fs.createReadStream` (`highWaterMark: 16 КБ`) та `stream.pipeline(readStream, res)` сервер автоматично призупиняв читання з диска, коли мережевий буфер заповнювався.

## Цикл подій Node.js та подія `"error"` в EventEmitter

### 1. Що буде, якщо обробник HTTP на 300 мс займе цикл подій?

Node.js виконує JavaScript-код в одному головному потоці поверх циклу подій `libuv` (фази: `timers` → `pending callbacks` → `idle/prepare` → `poll` → `check` → `close callbacks`).

Якщо синхронний код в обробнику HTTP-запиту заблокує стек на 300 мс:

- **Зупиняється фаза `poll`:** сервер не приймає нові TCP/HTTP-з’єднання і не зчитує вхідні фрейми WebSocket з сокетів ОС.
- **Затримуються фази `timers` і `check`:** усі таймери (`setTimeout` для таймауту `join` на 5 с, `setInterval` для `ping` раз на 15 с) зсуваються щонайменше на 300 мс.
- **Деградує латентність для всіх гравців одночасно:** один важкий запит одного клієнта заморожує чат і вхід у кімнати для всіх інших користувачів.

### 2. Чому подія `"error"` без слухача валить увесь процес?

У класі `EventEmitter` із модуля `node:events` подія з назвою `"error"` має спеціальну поведінку.

Якщо під час виклику:

```javascript
emitter.emit("error", err);
```

на об’єкті не зареєстровано жодного слухача (`emitter.on("error", ...)`), Node.js викидає переданий об’єкт помилки як неперехоплений виняток (`uncaughtException`), виводить стек у `stderr` і аварійно завершує процес із ненульовим кодом виходу (`exit code 1`).

Саме тому в `Room` додано слухач `this.on("error", ...)`, а потоки в `MatchLogger` об’єднані через `stream.pipeline()`, який централізовано перехоплює помилки всіх потоків у ланцюжку.

## Reflection (Питання до захисту)

### Чим Node.js відрізняється від браузера?

У браузері є `window`, DOM, Web Audio, Canvas API і діє модель безпеки Same-Origin Policy.

У Node.js немає DOM, натомість є:

- глобальний об’єкт `process`;
- прямий доступ до файлової системи (`node:fs`);
- низькорівневі мережеві сокети (`node:net`, `node:http`);
- бінарні буфери `Buffer`;
- потоки `node:stream` поверх бібліотеки `libuv`.

### Як працює механізм backpressure у потоках Node.js?

Коли джерело даних (`Readable`, наприклад `fs.createReadStream`) читає швидше, ніж споживач (`Writable`, наприклад повільний HTTP-сокет `res`) встигає відправляти їх у мережу, внутрішній буфер `Writable` заповнюється понад `highWaterMark`, і `write()` повертає `false`.

Функція `stream.pipeline()` автоматично ставить `Readable` на паузу (`pause()`) і відновлює читання (`resume()`), щойно споживач звільнить буфер і згенерує подію `"drain"`.

### Навіщо в `wsServer.js` потрібні ping/pong та ліміт `bufferedAmount`?

TCP-з’єднання може обірватися «тихо» (наприклад, при втраті Wi-Fi без надсилання FIN-пакета).

- **Ping/pong** дозволяє серверу виявити «мертвого» клієнта за 30 с і очистити його місце в кімнаті.
- Перевірка `ws.bufferedAmount` захищає пам’ять сервера від переповнення, якщо клієнт із повільним інтернетом не встигає вичитувати широкомовні повідомлення кімнати.

### Чому в HTTP-сервері обов’язково перевіряти `..` у шляху запиту?

Без перевірки запит на кшталт:

```http
GET /../../server/src/config.js
```

дозволив би зловмиснику вийти за межі каталогу `client/dist` (Directory / Path Traversal) і прочитати вихідний код сервера або конфігураційні файли.
