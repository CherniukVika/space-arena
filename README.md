# Space Arena — Lab 01

**Автор:** Чернюк Вікторія Андріївна, група Б-121-23-1-ПІ
**Тема гри:** Космічна ракета

Мультиплеєрна браузерна гра в реальному часі (клієнт: Vite + Canvas 2D, сервер: Node.js — у наступних лабораторних). Лабораторна 1: ігровий цикл з фіксованим кроком симуляції, ввід як замикання, чиста функція фізики, малювання на canvas.

## Запуск

```bash
npm install
npm run dev     # http://localhost:5173
npm run lint    # Biome
node scripts/dt-experiment.js
```

Керування: `←` / `→` (або `A` / `D`) — поворот, `↑` / `W` / `Пробіл` — тяга. На краях арени ракета «загортається» на протилежний бік.

Параметри в адресі для експериментів:

| Параметр  | Значення                                           |
| --------- | -------------------------------------------------- |
| `?mode=`  | `fixed` (за замовчуванням), `interval`, `variable` |
| `&block=` | штучне блокування головного потоку в `render`, мс  |

## Архітектура

- `src/loop.js` — `createLoop()`: `requestAnimationFrame` + акумулятор. Симуляція кроком `dt = 1/60`, рендер з інтерполяцією (`alpha`). Режими `fixed`, `variable`, `interval` потрібні для експериментів.
- `src/input.js` — `createInput()`: замикання над приватним `Set` натиснутих клавіш, назовні лише `read()` і `dispose()`.
- `src/physics.js` — `integrate(ship, input, dt, arena)`: чиста функція без DOM і без читання часу.
- `src/render.js` — Canvas 2D з урахуванням `devicePixelRatio`: спрайт ракети та процедурно згенерований фон космосу (градієнт, туманності, зорі).
- `src/main.js` — збирає все докупи й виводить HUD (steps/s, frames/s, час кадру).
- `scripts/dt-experiment.js` — запуск `integrate` у Node для експерименту 3.

### Експеримент 0 — еталон

Симуляція йде рівно 60 кроків на секунду, а кадрів малюється 165 (частота монітора). Отже, частота симуляції не залежить від частоти рендеру: на кожен крок припадає приблизно 2,75 кадру, і саме інтерполяція (`alpha`) робить рух плавним між кроками.

### Експеримент 1 — блокуючий цикл у кадрі

У `render` додано `busyWait(50)` та `busyWait(100)`. Frame time зріс до 50,3 і 100,6 мс, а frames/s упали зі 165 до 19,9 і 9,9, тобто майже рівно `1000 / blockMs`. При цьому **steps/s лишився ≈ 60** (60,6 і 59,6): акумулятор за довгий кадр виконує кілька кроків поспіль (≈ 3 при 50 мс і ≈ 6 при 100 мс), тому швидкість ракети у «ігровому» часі не змінилась. Візуально ж рух став смикатися: ми бачимо лише кожен 3-й або 6-й стан симуляції.

**Пояснення через event loop.** JavaScript виконується в одному потоці. Колбек `requestAnimationFrame` виконується як синхронна задача: поки він не завершився (а в ньому крутиться `busyWait`), стек викликів не порожній, і event loop не може взятися ні за наступну задачу (наприклад, подію `keydown` із черги), ні за етап відмальовування сторінки. Тому один довгий кадр затримує і малювання, і обробку вводу: натискання клавіші потрапить у `down` лише після завершення кадру, тобто з запізненням до довжини кадру. Максимальний кадр (54,7 і 103,1 мс) значно менший за обмеження `maxFrameMs = 250`, тому захист від «спіралі смерті» тут не спрацьовував; він потрібен, щоб після дуже довгої паузи акумулятор не накопичив сотні кроків, які знову затягнуть кадр.

### Експеримент 2 — `setInterval` замість `requestAnimationFrame`

Режим `interval` викликає і крок, і рендер у колбеку `setInterval(…, 1000/60)`. Результат: steps/s = frames/s = **62,4**, а не 60 і не 165. Значення 62,4 ≈ 1000/16: схоже, що інтервал 16,67 мс браузер округлив до 16 мс. Монітор показує 165 кадрів/с, а ми малюємо лише 62 — тобто 2–3 оновлення екрана підряд показують один і той самий кадр, що видно як менша плавність, ніж у еталоні.

**Пояснення через event loop.** `setInterval` ставить у чергу звичайну _task_ не раніше за вказаний час, і він не знає про відмальовування. Етап «rendering» event loop (там виконуються колбеки `requestAnimationFrame` і відбувається paint) працює за vsync монітора незалежно від таймера, тому кадри симуляції та кадри екрана не збігаються. Якщо головний потік зайнятий, колбек таймера запізнюється, і затримки накопичуються, а крок симуляції при цьому все одно вважається рівним 1/60 с, тому гра йде в реальному часі нерівно. Крім того, за документацією браузерів, у фонових вкладках таймери сильно сповільнюються (приблизно до одного виклику на секунду), тоді як `requestAnimationFrame` у фоні взагалі призупиняється. _(Фонову вкладку я окремо не вимірювала.)_

### Експеримент 3 — змінний крок замість фіксованого

У режимі `variable` у кожному кадрі викликається один `step(dt)` з реальним `dt`. Без навантаження це 165 кроків/с по ≈ 6 мс (`steps/s = frames/s = 165.0`). З `block=40` кадр триває 40,7 мс, кроків лише 24,6 за секунду, і кожен крок «стрибає» на ≈ 41 мс, тому ракета рухається ривками. Крок залежить від продуктивності комп'ютера, що небезпечно для мультиплеєра.

Щоб показати це числами без браузера, `integrate` (чиста функція) запускається в Node: ракета 3 с летить з постійною тягою вправо (`node scripts/dt-experiment.js`).

Запуск 1:

```

fixed  60 Hz: x=589.494  vx=304.529
fixed 144 Hz: x=589.737  vx=305.420
fixed 240 Hz: x=589.804  vx=305.675
variable (random dt) #1: x=589.351  vx=303.956
variable (random dt) #2: x=589.355  vx=303.979
variable (random dt) #3: x=589.290  vx=303.906
```

Запуск 2:

```
fixed  30 Hz: x=589.059  vx=303.007
fixed  60 Hz: x=589.494  vx=304.529
fixed 144 Hz: x=589.737  vx=305.420
fixed 240 Hz: x=589.804  vx=305.675
variable (random dt) #1: x=589.317  vx=303.894
variable (random dt) #2: x=589.354  vx=304.013
variable (random dt) #3: x=589.343  vx=303.886
```

Висновки:

1. Рядки `fixed` ідентичні між запусками: симуляція **детермінована**, тобто та сама послідовність вводів завжди дає той самий результат.
2. Рядки `variable` щоразу різні (наприклад, `x` від 589.290 до 589.355 при однаковому вводі): результат залежить від випадкових `dt`, тобто **недетермінований**.
3. Навіть для фіксованого кроку результат трохи залежить від самого значення `dt` (30 Гц → 589.059, 240 Гц → 589.804): метод інтегрування наближений. Тому в мультиплеєрі клієнт і сервер повинні використовувати **той самий** фіксований `dt`, інакше їхні стани розходитимуться.

## Reflection

- **Чому `requestAnimationFrame`, а не `setInterval`?** rAF викликається в етапі відмальовування, синхронізований з монітором і призупиняється у фоні. `setInterval` ставить звичайні задачі з округленням і дрейфом, не знаючи про рендер (експеримент 2: 62,4 замість 60 і 165).
- **Навіщо акумулятор?** Він відв'язує частоту симуляції від fps: кожен кадр додає реальний час в акумулятор, ми віднімаємо по `dt = 1/60`, доки є що віднімати, а залишок `acc / dt` — це `alpha` для інтерполяції рендеру.
- **Що таке «спіраль смерті» і як її уникнуто?** Якщо крок симуляції триває довше за `dt`, кожен кадр потребує більше кроків, ніж попередній, і цикл не наздоганяє. Захист: `maxFrameMs = 250` обмежує час, який кадр може додати до акумулятора.
- **Task і microtask.** Після кожної task event loop повністю виконує чергу microtask (Promise `.then`, `queueMicrotask`) і лише потім може відмалювати сторінку та взяти наступну task. Тому `Promise.resolve().then(...)` спрацює раніше за `setTimeout(..., 0)`, а нескінченний ланцюг microtask заблокує рендер ще сильніше за довгу task.
- **Де тут замикання?** У `createInput`: `down`, `onKeyDown`, `onKeyUp` живуть у скоупі функції, доступні лише через повернуті `read()` і `dispose()` — приватний стан без класів.
- **Чому `integrate` чиста і навіщо?** Вона залежить лише від аргументів і не має побічних ефектів, тому її можна запускати в Node (як у `dt-experiment.js`), на сервері, тестувати й відтворювати результат.
- **`let` / `const`.** Обидва мають блочну область видимості та TDZ, на відміну від `var` (функціональна область і hoisting). `const` — для незмінних посилань (`dt`, `ctx`), `let` — для змінних, що перепризначаються (`last`, `acc`).
- **Навіщо `devicePixelRatio`?** На екранах з DPR > 1 canvas із буфером у CSS-пікселях розтягується і виглядає розмитим. Ми збільшуємо буфер у `dpr` разів, масштабуємо контекст, а CSS-розмір лишаємо логічним.
- **Чому ES-модулі?** Кожен файл має власну область видимості, залежності явні (`import` / `export`), `type="module"` вмикає strict mode та відкладене виконання, а Vite збирає модулі в бандл.
