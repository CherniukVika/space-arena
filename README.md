## Архітектура асинхронного шару (Lab 03)

### `src/assets/loader.js`

Завантажувачі `fetchJson`, `loadJson`, `loadImage`, `loadAudio`.

Усі приймають `AbortSignal`, перевіряють `res.ok` (кидають `HttpError`) та обгорнуті у `withRetry()` з exponential backoff + jitter:

```text
baseDelayMs * 2^attempt + random
```

При цьому запити зі статусом 4xx та скасовані через `AbortError` не повторюються.

Функція `loadAll()` завантажує ресурси паралельно через `Promise.all` і передає прогрес кожного файлу в колбек `onProgress`.

### `src/ui/loadingScreen.js`

Рендер екрана завантаження безпосередньо на `<canvas>` зі шкалою прогресу та статусом кожного файлу:

```text
[  ]   — очікування
[..]   — завантаження
[OK]   — успішно
```

Гра стартує виключно після `await loadAll(...)`.

### `src/events/bus.js`

Шина подій `GameBus extends EventTarget`.

Симуляція (`World`, `Ship`) не імпортує `audio.js` чи DOM-елементи, а відправляє події `CustomEvent`:

- `fired`;
- `hit`;
- `exploded`.

### `src/audio/audio.js`

`AudioSystem` на базі `AudioContext`.

Аудіофайли декодуються (`decodeAudioData`) ще на етапі завантаження, а сам контекст розблоковується (`ctx.resume()`) після кліку гравця на кнопку `JOIN ARENA`.

### `src/lobby/lobby.js` та `src/ui/lobbyView.js`

Клас `Lobby extends EventTarget` опитує `/api/rooms.json` кожні 3 секунди, накладаючи `AbortSignal.timeout(2500)` на кожен запит.

Щойно гравець натискає `JOIN ARENA`, викликається `lobby.stop()`, який зупиняє інтервал і робить `abort()` активного мережевого запиту.

## Порівняння завантаження: Sequential `await` vs Concurrent `Promise.all`

Вимірювання проведено для 4 ресурсів із `manifest.json` (`sheet.png`, `shoot.wav`, `hit.wav`, `explode.wav`) у браузері Chrome (165 Гц) без кешу (`Disable cache`) та з імітацією мережевої затримки ~40 мс на запит.

| Режим завантаження               | Механізм у коді                                                             | Загальний час (4 файли) | Поведінка прогрес-бару                                                        |
| -------------------------------- | --------------------------------------------------------------------------- | ----------------------- | ----------------------------------------------------------------------------- |
| Sequential (`for..of` + `await`) | Кожен наступний `fetch` чекає завершення попереднього (`t1 + t2 + t3 + t4`) | ~168 мс                 | Крокує строго по одному файлу: 25% → 50% → 75% → 100%                         |
| Concurrent (`Promise.all`)       | Усі запити стартують одночасно, загальний час = `max(t1, t2, t3, t4)`       | ~49 мс                  | Усі файли переходять у loading, далі швидко завершуються в довільному порядку |

### Висновок

Паралельне завантаження через `Promise.all` у `loadAll()` скоротило час очікування на старті в ~3.4 раза, оскільки браузер завантажує спрайтшит і аудіофайли одночасно, не простоюючи в очікуванні RTT кожного окремого запиту.

## П’ять головоломок порядку виконання (Task / Microtask / rAF)

### Головоломка 1: `await` розбиває функцію на синхронну частину та мікрозадачу

```javascript
console.log("1");

async function run() {
	console.log("2");
	await Promise.resolve();
	console.log("3");
}

run();
console.log("4");
```

**Вивід:**

```text
1, 2, 4, 3
```

**Пояснення:** Тіло async-функції до першого `await` виконується синхронно (2), а код після `await` планується в чергу мікрозадач і спрацьовує лише після завершення синхронного стеку (4).

---

### Головоломка 2: `setTimeout` всередині `.then()`

```javascript
Promise.resolve().then(() => {
	console.log("A");
	setTimeout(() => console.log("B"), 0);
});

setTimeout(() => console.log("C"), 0);

Promise.resolve().then(() => console.log("D"));
```

**Вивід:**

```text
A, D, C, B
```

**Пояснення:** Спочатку спорожнюється вся черга мікрозадач (A, D), де A ставить макрозадачу B у кінець черги таймерів після вже запланованого C.

---

### Головоломка 3: Мікрозадачі vs `requestAnimationFrame`

```javascript
requestAnimationFrame(() => console.log("rAF"));

setTimeout(() => console.log("timeout"), 0);

Promise.resolve().then(() => console.log("microtask"));

console.log("sync");
```

**Вивід:**

```text
sync, microtask, timeout, rAF
```

або `rAF` перед `timeout`, залежно від фази vsync.

**Пояснення:** `sync` і `microtask` завжди виконуються до завершення поточного тіку event loop, тоді як `setTimeout` (макрозадача) та `requestAnimationFrame` (фаза рендерингу перед paint) чекають наступних кроків циклу.

---

### Головоломка 4: `await` не-проміса (примітиву)

```javascript
async function f() {
	console.log("start");
	const x = await 42;
	console.log(x);
}

f();

Promise.resolve().then(() => console.log("promise"));
```

**Вивід:**

```text
start, promise, 42
```

**Пояснення:** `await 42` неявно обгортає значення в `Promise.resolve(42)` і віддає керування event loop, тому раніше поставлена мікрозадача `promise` виконується перед відновленням `f()`.

---

### Головоломка 5: Ланцюжок `.then()` після `catch()`

```javascript
Promise.reject("err")
	.then(() => console.log("1"))
	.catch(() => console.log("2"))
	.then(() => console.log("3"));
```

**Вивід:**

```text
2, 3
```

**Пояснення:** Перший `.then()` пропускається через відхилений стан проміса, `catch()` перехоплює помилку і повертає виконаний проміс (`undefined`), тому наступний `.then()` (3) успішно спрацьовує.

## Галерея збоїв (Fault Tolerance)

| Сценарій збою                              | Як відтворити                                                                                                | Поведінка системи (без падіння гри)                                                                                                                                                  |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 404 спрайта або маніфесту                  | Відкрити `/?manifest=/404.json` або вказати неіснуючий шлях у `manifest.json`                                | `fetchJson` виявляє `!res.ok` (статус 404), `withRetry` розпізнає код 4xx і не робить зайвих повторів, прогрес-бар стає червоним із текстом помилки, з’являється кнопка Retry.       |
| Таймаут мережі                             | У DevTools → Network увімкнути Offline або Slow 3G під час опитування лобі (`timeoutMs: 2500`)               | `AbortSignal.timeout(2500)` автоматично перериває завислий запит у `Lobby.refresh()`, у лобі виводиться повідомлення `Room fetch failed`, а таймер спробує оновити список через 3 с. |
| Abort посеред завантаження / виходу з лобі | Натиснути кнопку Cancel Load на екрані завантаження або натиснути JOIN ARENA під час активного запиту кімнат | Викликається `controller.abort()`, `fetch` і `Image` миттєво зупиняються (`AbortError` ігнорується в лобі без помилок у консолі), на екрані завантаження з’являється кнопка Retry.   |
| Битий JSON                                 | Передати файл із невалідним синтаксисом JSON у `manifest.json` або `rooms.json`                              | `res.json()` відхиляє проміс із `SyntaxError`, `withRetry` робить 3 спроби з exponential backoff, після чого коректно показує помилку в UI та дозволяє повторити запит через Retry.  |

## Reflection (Питання до захисту)

### Чим `Promise.all` відрізняється від `Promise.allSettled`, `Promise.race` та `Promise.any`?

- **`Promise.all`** чекає виконання всіх промісів і миттєво відхиляється при першій помилці (fail-fast — ідеально для обов’язкових ресурсів гри).
- **`Promise.allSettled`** чекає завершення всіх промісів незалежно від результату (`fulfilled` або `rejected`).
- **`Promise.race`** повертає результат першого завершеного проміса (успішного чи з помилкою).
- **`Promise.any`** повертає результат першого успішно виконаного проміса.

### Навіщо в retry додавати jitter до exponential backoff?

Якщо сервер тимчасово впав, а сотні клієнтів одночасно роблять повтори строго через 200 мс → 400 мс → 800 мс, вони створять синхронні піки навантаження (**thundering herd problem**).

Випадковий зсув (`jitter`) розмазує повторні запити в часі.

### Чому `AudioContext` не можна запустити автоматично при завантаженні сторінки?

Політика Autoplay Policy сучасних браузерів блокує відтворення звуку без взаємодії користувача (suspended стан), щоб захистити від нав’язливої реклами.

Тому буфери ми декодуємо заздалегідь під час `loadAll()`, а `audioCtx.resume()` викликаємо всередині обробника кліку на кнопку `JOIN ARENA`.

### Навіщо використовувати шину подій `EventTarget` замість прямого виклику `audio.play()` всередині `Ship.fire()`?

Це розриває жорстку зв’язаність (**decoupling**) між симуляцією та підсистемами представлення (звуком, HUD, аналітикою).

Клас `Ship` і `World` залишаються чистими від браузерного Web Audio API — їх можна без змін запускати в headless-режимі на Node.js сервері.
